C++缓存系统项目

背景介绍

什么是缓存？

缓存是将高频访问的数据暂存到内存中，是加速数据访问的存储，降低延迟，提高吞吐率的利器。

为什么要实现缓存系统?

因缓存的使用相关需求，通过牺牲一部分服务器内存，减少对磁盘或者数据库资源进行直接读写，可换取更快响应速度，尤其是处理高并发的场景，负责存储经常访问的数据，通过设计合理的缓存机制提高资源的访问效率。由于服务器的内存是有限的，我们不能把所有数据都存放在内存中，因此需要一种机制来决定当使用内存超过一定标准时，应该删除哪些数据，这就涉及到缓存淘汰策略的选择。

在什么地方加缓存？

缓存对于每个开发者来说是相当熟悉了，为了提高程序的性能我们会去加缓存，但是在什么地方加缓存，如何加缓存呢？举个例子：假设一个网站，需要提高性能，缓存可以放在浏览器，可以放在反向代理服务器，还可以放在应用程序进程内，同时可以放在分布式缓存系统中。

从用户请求数据到数据返回，数据经过了浏览器、CDN、代理服务器、应用服务器，以及数据库各个环节。每个环节都可以运用缓存技术。从浏览器/客户端开始请求数据，通过HTTP配合CDN获取数据的变更情况，到达代理服务器(Nginx)可以通过反向代理获取静态资源。再往下来到应用服务器可以通过进程内（堆内）缓存，分布式缓存等方式获取数据。如果以上所有缓存都没有命中数据，才会回源到数据库。

缓存的顺序：用户请求->HTTP缓存->CDN缓存->代理服务器缓存->进程内缓存->分布式缓存->数据库

距离用户越近，缓存能够发挥的效果越好。

FIFO缓存技术（先进后出）

先进先出算法，是最简单的页面替换策略，按照页面进入内存的顺序来决定替换哪个页面。即优先淘汰最早进入内存的页面，不论这些页面之后是否被频繁访问。但是FIFO可能会导致“Belady异常”，即随着分配给进程的物理块数增加，缺页次数反而增加。

  • FIFO 完全按照页面进入内存的时间替换，与“未来是否还会访问”无关。
  • 当物理块增加时，旧页面的生命周期可能被延长，导致新访问的页面更早把常用页挤掉。
  • 这种替换次序变化，可能让“好不容易留住的常用页”被提前换出，缺页次数反而增加。

FIFO工作流程

假设缓存大小 = 3;访问序列：A B C A D B E

  • A → 缓存：[A]
  • B → 缓存：[A, B]
  • C → 缓存：[A, B, C]（满）
  • A → 命中，FIFO 不改变顺序，还是 [A,B,C]
  • D → 淘汰最早 A → 缓存：[B, C, D]
  • B → 命中，顺序不变
  • E → 淘汰最早 B → 缓存：[C, D, E]
  • 关键点：即使 A 刚被访问过，它依然是最早进的，照样被踢。

FIFO 结构实现

  • 用 队列（Queue） 维护顺序
  • 用 哈希表 / 集合 快速判断是否命中
  • 插入 / 删除都是 O (1)

LRU 缓存技术算法

最近最少使用，它的设计原则借鉴了时间局部性原理，该算法认为如果数据最近被访问过，那么将来被访问的几率也更高，反之亦然。其原理是将数据按照其被访问的时间形成一个有序序列，最久未被使用的数据应该最早被淘汰掉，即当缓存空间被占满时，缓存内最长时间未被使用的数据将被淘汰掉。

简单来说：个人理解：使用的热点高频数据就会放到最前面进行读取，如下图所示：

潜在问题：淘汰热点数据，如果有个数据在1个小时的前59分钟访问了1万次(可见这是个热点数据),再后一分钟没有访问这个数据，但是有其他的数据访问，就导致了我们这个热点数据被淘汰。

算法流程

为了实现高效的 get（读取）和 put（写入）操作（通常要求时间复杂度为 O(1)），LRU 算法通常采用 “哈希表 + 双向链表” 的组合数据结构。

  • 哈希表 (HashMap)：负责存储 key 到链表节点的映射，实现 O(1) 的快速查找。
  • 双向链表 (Doubly Linked List)：负责维护数据的“使用时序”。链表头部代表“最近使用”，尾部代表“最久未使用”。

重点算法流程：

读取数据部分：

  1. 查找：首先在哈希表中查找 key 是否存在。
  2. 未命中：如果 key 不存在，直接返回一个特定值（如 -1 或 null）。
  3. 命中：如果 key 存在：
    • 通过哈希表找到对应的链表节点。
    • 获取该节点中存储的 value。
    • 关键步骤：将该节点从链表的当前位置移除，并移动到链表的头部。这一步是为了标记该数据为“最近使用”。
    • 返回 value。

写入数据部分：

  1. 查找：首先在哈希表中查找 key 是否已存在。
  2. Key 已存在 (更新操作)：
    • 更新该节点中的 value 为新值。
    • 同样，将该节点移动到链表的头部，标记为“最近使用”。
  3. Key 不存在 (新增操作)：
    • 检查容量：判断当前缓存是否已满（即哈希表/链表的大小是否达到容量上限）。
    • 若已满，执行淘汰：
      • 找到链表尾部的节点（即“最久未使用”的数据）。
      • 从哈希表中删除该尾部节点的 key。
      • 从链表中删除该尾部节点。
    • 插入新数据：
      • 创建一个包含 key 和 value 的新节点。
      • 将新节点插入到链表的头部。
      • 在哈希表中建立 key 到这个新节点的映射。
操作 核心步骤 目的
get(key) 1. 哈希表查找
2. 找到则移动到链表头部		 读取数据并更新其为“最近使用”
put(key, value) 1. 哈希表查找
2. 若存在则更新并移到头部
3. 若不存在则检查容量，必要时淘汰尾部节点，再插入新节点到头部		 写入/更新数据并维护缓存容量和使用时序

学习完基础的LRU缓存算法实现之后，大家不难发现他身上的缺点：

  • 对访问模式不敏感：如果是循环的一次性遍历大量不重复的数据（如A->B->C->D->A->B->…），LRU可能逐步清空，几乎无法命中。
  • 缓存污染：如果加载一些不再会被访问的冷数据（如一次性数据），将原有的热点数据挤出，冷数据留在缓存中，降低了缓存的利用率。
  • 不适用于某些场景：在某些场景下，最近最少使用并不代表最不重要或最少需要。
  • 锁的粒度大：多线程高并发的访问下，同步等待将是一笔极大的时间开销。

LRU-K缓存技术

LRU-k算法是对LRU算法的改进，基础的LRU算法被访问数据进入缓存队列只需要访问(put、get)一次就行，但是现在需要被访问k（大小自定义）次才能被放入缓存中，基础的LRU算法可以看成是LRU-1。

LRU-k算法有两个队列一个是缓存队列，一个是数据访问历史队列。当访问一个数据时，首先将其添加进入访问历史队列并进行累加访问次数，当该数据的访问次数超过k次后，才将数据缓存到缓存队列，从而避免缓存队列被冷数据所污染。同时访问历史队列中的数据也不是一直保留的，也是需要按照LRU的规则进行淘汰的。LRU-k执行过程如图：

一般情况下，当k的值越大，缓存的命中率越高，但也使得缓存难以淘汰。综合来说，k = 2 时性能最优。

大家试想一下当多个线程同时访问一个LRU时（LFU同理），由于锁的粒度大，是不是会造成长时间的同步等待，那如果是多个线程同时访问多个LRU缓存呢，是不是同步等待时间大大减少了。

普通的lruCache和lfuCache在高并发情况下耗时增加的原因分析：

线程安全的lfuCache中有锁的存在。每次读写操作之前都有加锁操作，完成读写操作之后还有解锁操作。在低QPS下，锁的竞争的耗时基本可以忽略；但在高并发的情况下，大量的时间消耗在等待锁的操作上，导致耗时增长。

HashLruCache和HashLfuCache适应高并发场景：：

针对大量同步等待操作导致耗时增加的情况，解决方案就是尽量减小临界区。引入hash机制，对全量数据做分片处理，在原有LfuCache的基础上形成HashLfuCache，以降低查询耗时。

HashLfuCache引入哈希算法，将缓存数据分散到N个LfuCache上，查询时也按照相同的哈希算法，先获取数据可能存在的分片，然后再去对应的分片上查询数据。这样可以增加lfu的读写操作的并行度，减少同步等待的耗时。

Lfu缓存技术

最近使用频率高的数据很大概率将会再次被使用,而最近使用频率低的数据,将来大概率不会再使用。

做法：把使用频率最小的数据置换出去。这种算法更多是从使用频率的角度（但是当缓存满时，如果最低访问频次的缓存数据有多个，就需要考虑哪个元素最近最久未被访问）去考虑的。

学完基础的LFU，大家不难发现其身上还有很多待优化点：

  • 频率爆炸问题：对于长期驻留在缓存中的热数据，频率计数可能会无限增长，占用额外的存储空间或导致计数溢出。
  • 过时热点数据占用缓存：一些数据可能已经不再是热点数据，但因访问频率过高，难以被替换。
  • 冷启动问题：刚加入缓存的项可能因为频率为1而很快被淘汰，即便这些项是近期访问的热门数据。
  • 不适合短期热点：LFU对长期热点数据表现较好，但对短期热点数据响应较慢，可能导致短期热点数据无法及时缓存。
  • 缺乏动态适应性：固定的LFU策略难以适应不同的应用场景或工作负载。
  • 锁的粒度大，多线程高并发访问下锁的同步等待时间过长。

最大平均访问次数限制

参考：https://blog.csdn.net/yunshuipiao123/article/details/98958750
在LFU算法之上，引入访问次数平均值概念，当平均值大于最大平均值限制时将所有结点的访问次数减去最大平均值限制的一半或者一个固定值。相当于热点数据“老化”了，这样可以避免频次计数溢出，也可以缓解缓存污染。

加上最大平均访问次数限制的LFU代码

设置最大平均访问次数的值解决了什么问题？

  1. 防止某一个缓存的访问频次无限增加，而导致的计数溢出。
  2. 旧的热点缓存，也就是该数据之前的访问频次很高，但是现在不再被访问了，也能够保证他在每次访问缓存平均访问次数大于最大平均访问次数的时候减去一个固定的值，使这个过去的热点缓存的访问频次逐步降到最低，然后从内存中淘汰出去
  3. 一定程度上是对新加入进来的缓存，也就是访问频次为1的数据缓存进行了保护，因为长时间没被访问的旧的数据不再会长期占据缓存空间，访问频率会逐步被降为小于1最终淘汰。

memory库

  • std::unique_ptr: 表示对某个对象的独占所有权。同一时间只能有一个 unique_ptr 指向该对象。它不能被复制，但可以通过 std::move 转移所有权。当 unique_ptr 离开其作用域或被销毁时，它会自动释放所管理的对象。
  • std::shared_ptr: 表示对某个对象的共享所有权。多个 shared_ptr 可以指向同一个对象，内部通过引用计数来跟踪有多少个指针指向该对象。当最后一个指向该对象的 shared_ptr 被销毁时，对象才会被释放。
  • std::weak_ptr: 一种弱引用指针，通常与 std::shared_ptr 配合使用。它指向一个由 shared_ptr 管理的对象，但不会增加引用计数。它的主要作用是解决 shared_ptr 可能导致的循环引用问题。

简单来说：

1. unique_ptr 表示对象独占，不可拷贝，但是可以通过move方法转移
2. shared_ptr 表示对象共享，内部有一个“计数器”（引用计数）
3. weak_ptr 专门配合 shared_ptr 使用。
注意：weak_ptr通常解决死锁问题，例如：A 指向 B，B 指向 A。如果是两个 shared_ptr，它们互相引用，计数永远降不到 0，导致内存泄漏。
解决方案：把其中一边换成 weak_ptr，它不增加计数，打破死锁。

关键字

  • explicit 是 C++ 中一个用于增强类型安全的关键字，它的核心作用是禁止编译器进行隐式类型转换。
  • virtual 实现运行时多态性。简单来说，它允许你通过基类的指针或引用，去调用派生类中重新定义的函数版本，从而让程序在运行时根据对象的实际类型来决定执行哪段代码。
