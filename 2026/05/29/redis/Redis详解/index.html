1. Redis 是什么

Redis（Remote Dictionary Server，远程字典服务）是一个开源的、基于内存的高性能键值存储系统。

核心特点：

特点 说明
基于内存 数据存储在 RAM 中，读写速度极快（10万+ QPS）
键值存储 以 key-value 的形式组织数据，key 是字符串，value 支持多种类型
单线程模型 命令执行是单线程的，避免了锁竞争，保证了原子性
IO 多路复用 使用 epoll/kqueue 实现高并发连接处理
可持久化 支持将内存数据落盘，防止重启后数据丢失
支持丰富数据结构 不仅仅是简单的 key-value，还支持 List、Hash、Set 等

2. 为什么用 Redis

2.1 传统数据库的瓶颈

传统数据库的数据存储在磁盘上，每次读写都需要磁盘 I/O，即使有索引优化，在高并发场景下仍然会成为瓶颈。

2.2 Redis 的解决思路

将热点数据放入 Redis（内存），应用优先从 Redis 读取，大幅降低数据库压力。

2.3 适用场景

场景 说明
缓存 最常见的用法，缓存数据库查询结果、页面、Session 等
计数器 文章阅读量、点赞数，利用 Redis 原子自增操作
排行榜 利用 Sorted Set 实时排序
分布式锁 利用 SETNX / SET ... NX EX 实现跨进程互斥
消息队列 利用 List（BRPOP）或 Stream 实现简单的消息传递
限流 利用计数器 + 过期时间实现接口限流
会话存储 分布式环境下共享用户 Session

6. 特殊数据类型

6.1 Bitmap 位图

本质上是 String 类型，但可以按 位（bit） 操作。每个 bit 只有 0 或 1，适合表示布尔状态。

使用场景： 用户签到、在线状态、布隆过滤器底层。

6.2 HyperLogLog 基数统计

用于统计集合中 不重复元素的数量（基数），误差约 0.81%，但只需 12KB 内存。

使用场景： 网站 UV（独立访客数）统计。

6.3 Stream 流

Redis 5.0 引入，专为消息队列设计，支持消费者组，弥补了 List 作为消息队列的不足。

使用场景： 需要持久化、消费者组、消息确认的正式消息队列场景。

7. 键（Key）管理

8. 过期策略与内存淘汰

8.1 过期删除策略

Redis 中设置了过期时间的键不会在到期时立即被删除，而是采用两种策略结合：

策略 机制 特点
惰性删除 每次访问键时检查是否过期，过期则删除 对 CPU 友好，但可能有大量过期键未被访问而占用内存
定期删除 每隔一段时间随机检查一批键，删除其中过期的 折中方案，不会太频繁也不会漏太多

8.2 内存淘汰策略

当 Redis 内存达到上限（maxmemory）时，需要淘汰一些数据来腾出空间：

策略 说明
noeviction 不淘汰，写命令直接报错（默认）
allkeys-lru 从所有键中淘汰最近最少使用的
volatile-lru 从设置了过期时间的键中淘汰最近最少使用的
allkeys-lfu 从所有键中淘汰使用频率最低的（Redis 4.0+）
volatile-lfu 从设置了过期时间的键中淘汰使用频率最低的
allkeys-random 随机淘汰
volatile-random 从设置了过期时间的键中随机淘汰
volatile-ttl 优先淘汰即将过期的键

推荐： 大多数场景使用 allkeys-lru。

9. 持久化机制

Redis 的数据在内存中，如果进程崩溃或重启，数据会丢失。持久化机制就是将内存数据写入磁盘。

9.1 RDB 快照

在指定时间间隔内，将内存中的数据快照写入磁盘文件（dump.rdb）。

配置（redis.conf）：

优点：

  • 文件紧凑，适合备份和恢复
  • 恢复大数据集时速度比 AOF 快

缺点：

  • 可能丢失最后一次快照之后的数据
  • 快照时如果数据量大，fork() 子进程可能耗时较长

9.2 AOF 日志

将每次写操作追加到日志文件（appendonly.aof），重启时重新执行日志恢复数据。

配置（redis.conf）：

AOF 重写： 当 AOF 文件过大时，Redis 会根据当前内存数据重新生成一份精简的 AOF 文件。

优点：

  • 数据安全性更高（最多丢失 1 秒数据）
  • AOF 文件可读，便于理解和修复

缺点：

  • 文件通常比 RDB 大
  • 恢复速度比 RDB 慢

9.3 混合持久化

Redis 4.0+ 支持，在 AOF 重写时，将 RDB 格式的数据和 AOF 增量命令混合写入同一个文件。

推荐：同时开启 RDB 和 AOF（混合持久化），兼顾恢复速度和数据安全。

10. 发布/订阅（Pub/Sub）

Redis 提供的发布/订阅模式，Publisher 向 Channel 发布消息，Subscriber 订阅 Channel 收取消息。

⚠️ 注意： Pub/Sub 的消息不会持久化，也没有消费者确认机制。如果需要可靠消息，请使用 Stream。

11. 事务（Transaction）

Redis 的事务将多个命令打包，按顺序执行，期间不会被其他命令插入。

重要特性：

特性 说明
命令入队 MULTI 之后的命令不会执行，而是进入队列
原子性 EXEC 时所有命令一次性执行，不会被其他客户端的命令打断
不支持回滚 如果某条命令执行失败，其他命令仍然会执行，不会回滚

Redis 的事务和关系数据库的事务不同，没有 ROLLBACK 机制。Redis 认为语法错误应该在开发阶段就发现。

14. 高可用与集群

14.1 主从复制

一个 Master 节点可以有多个 Slave（Replica）节点。Slave 自动同步 Master 的数据。

配置（Slave 节点的 redis.conf）：

同步过程：

  1. Slave 连接 Master，发送 PSYNC 命令
  2. Master 执行 BGSAVE 生成 RDB 快照，发送给 Slave
  3. Slave 加载 RDB 文件
  4. Master 将之后的写命令通过 replication buffer 发送给 Slave（增量同步）

优点： 读写分离，扩展读性能；数据冗余，提高可用性。

缺点： Master 宕机需要手动切换；写操作无法扩展。

14.2 Sentinel 哨兵

在主从复制的基础上，增加 Sentinel 进程来自动监控和故障转移。

Sentinel 的职责：

任务 说明
监控 不断检查 Master 和 Slave 是否正常运行
通知 当某个节点出现故障时，通过 API 通知管理员
自动故障转移 Master 宕机时，自动将一个 Slave 提升为新 Master
配置提供 客户端连接时，可以向 Sentinel 询问当前的 Master 地址

14.3 Cluster 集群

Redis 3.0+ 官方的分布式方案，通过数据分片将数据分布在多个节点上，支持水平扩展。

核心概念：

概念 说明
哈希槽（Hash Slot） 总共 16384 个槽，每个 key 通过 CRC16(key) % 16384 计算出槽位号
节点 每个节点负责一部分槽位
分片 数据根据槽位号分布到不同节点
副本 每个主节点可以有从节点，用于高可用

使用方式：

-c 参数表示以集群模式连接，自动处理槽位重定向。

三种方案对比：

主从复制 Sentinel Cluster
数据分片 ✗ ✗ ✓
自动故障转移 ✗ ✓ ✓
写扩展 ✗ ✗ ✓
复杂度 低 中 高
适用场景 读多写少 中小规模 大规模

16. 性能优化要点

16.1 避免大 Key

标准：

  • String 类型的 value > 10 KB
  • Hash/List/Set/ZSet 的元素个数 > 5000

16.2 避免热 Key

单个 Key 的 QPS 过高，集中在同一个节点上。

解决方案：

  • 拆分成多个子 Key：hot_key:0、hot_key:1、… hot_key:9
  • 本地缓存（Caffeine / Guava Cache）
  • 读写分离
